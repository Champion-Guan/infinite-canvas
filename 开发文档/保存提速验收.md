# 新项目保存提速（2026-10-24）

## 原因与改动

旧项目直接写浏览器 IndexedDB。新项目需要带类型编码、分片、通过本机服务写 SQLite，并校验真实提交回执。此前实现还有四项可避免的开销：

1. 已恢复或已经保存的 Blob URL，每次编辑仍读取、重传全部图片。当前命名空间含126处媒体引用，一代累计处理235,293,718字节（约224.4MiB，含重复引用），即使仅修改一段文字也会触发。
2. 原400ms尾随防抖在持续输入时不断延后，没有最长等待。
3. 每次分片判定反复序列化同一子树、重复计算字节大小和可内联深度。
4. 不可变分片串行等待HTTP查找与写入，并允许在途时不断排入过时完整快照。

保存业务改动限定在根目录 `扩展功能/本机存储/` 的四个功能模块：

- `应用值编码.mjs`：仅复用全部分片已经ACK的不可变Blob/URL描述；刷新解码后复用经读取验证的媒体。不缓存可变ArrayBuffer；失败不记作成功；描述复制避免外部修改缓存。画布汇总媒体上限提高到1GiB，仍保留有限恢复上限、单文件32MiB限制、磁盘余量和凭据安全端口。
- `分片值编码.mjs`：在单次计划内缓存精确UTF-8字节大小与内联深度。缓存不跨可变快照复用，格式、哈希、容量及深度规则保持。
- `分片应用存储.mjs`：不可变分片最多四路并发；同批全部收口才报告失败；所有分片收到ACK后才提交根目录CAS。原操作ID、失败恢复和冲突保护保持。
- `上游浏览器存储桥.ts`：空闲80ms提交，持续编辑最迟250ms启动；同键一代在途时只合并尚未发送的最新候选。flush等待在途和最后候选真实确认，失败操作仍留在原恢复队列。刷新完整读取并核验的基线显示“已保存”；新的待提交编辑仍显示“保存中”，不把初始化后的idle长期误报为保存中。

未降低SQLite同步等级、未关闭fsync、未提前显示“已保存”、未退回浏览器数据库。没有改动旧3000项目、启动额外工作台或触发收费生成。

## 测量与验收

- 使用已有Chrome `localhost:3001`（3000被旧项目占用自动顺延），沿用当前工作簿可见六个产品和104节点画布；整个存储实际有145个产品，53个不同媒体引用，均保留。
- 修复前：同一参数输入框增加临时标记，从自动化动作发起 `08:13:15.662Z` 到SQLite根目录提交 `08:13:56.206Z`，40,544ms。
- 首轮修复：恢复原参数，从动作发起 `08:21:56.984Z` 到真实提交 `08:21:59.451Z`，2,467ms。
- 分片并发后：同字段再次增加标记，从动作发起 `08:26:08.045Z` 到提交 `08:26:10.743Z`，2,698ms。动作时间包含浏览器自动化传递与前端更新，不是纯SQLite SQL执行时间，也不能等同所有画布的保证值。
- 同一实际命名空间、同一次对照运行：旧分片规划1,467ms，优化后222ms；126个分片，头哈希完全相同。另外四组空值、Unicode和合成画布的头哈希一致。
- 六组定向测试共130项通过：分片存储、分片故障矩阵、自动重连、值与媒体存储、保存状态、此次提速。
- 随后加入“在途只留最新候选”和读验基线状态的边界保护，相关三组33项复验全部通过，覆盖慢提交时连续20次编辑、末稿flush、ACK前状态、失败状态、刷新基线、自动重连及限量并发收口。
- 刷新读取SQLite后测速标记仍存在，51张页面图片全部加载成功。验收结束恢复原字段，数据库复核无任何测速标记；再次刷新核验。
- 来源检查：384文件一致，1,178处引用通过，无旧前端引用。

初次打开仍需读取与验证现有分片和媒体；本批主目标是编辑保存速度，不宣称启动加载已经达到旧浏览器库速度。

最后一轮自动构建另发现：开发输出设置为不清空，607个静态文件累计538,044,921字节，超过服务512MiB上限，导致新包不能接入。仅修正 `开发工具/开发版运行.mjs` 的 `emptyOutDir: true`；服务仍持有上一代内存快照，构建失败不会撤下当前页面。重新构建成功后静态输出52个文件、7,778,752字节（约7.4MiB）。不提高保护限额、不清理用户数据、不改端口，也不另开服务。

## 回退

源码快照继续仅保留最近五份。另提供此次四模块及构建输出设置的定向逆向补丁，避免回退其他已完成功能：

```sh
git apply --check 开发文档/保存提速回退.patch
git apply 开发文档/保存提速回退.patch
```

运行中的开发服务会自动装配构建，完成后刷新现有页面。不要手改 `.运行/3100源`；不要对正在监听构建的服务再并发执行 `dev:build`。本补丁只回退实现，不回退、覆盖或删除任何工作区数据。
