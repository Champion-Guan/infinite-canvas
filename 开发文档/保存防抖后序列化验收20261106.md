# 保存防抖后序列化验收

日期：2026-11-06。目标：减少 MacBook Air M1 8GB 连续编辑时的重复编码，同时保持保存回执、失败恢复和批量任务检查点正确。

## 原因与修改

原画布 Zustand 存储先执行 `JSON.stringify(value)`，再进入保存防抖。SQLite 写入虽然合并了，每次项目状态变化仍先遍历全部产品、节点和回收站。

现改成保存队列接收捕获不可变快照的编码函数。80ms 停笔或 250ms 最长等待到达、且上一笔提交结束后，只编码最新候选；显式排空立即提交。等待期间替换函数引用，不深复制对象，也不编码中间稿。

编码成功后立即释放捕获旧画布对象的函数，回执等待期间保留编码结果。在途请求仍使用原内容；失败请求仍由原 SQLite 恢复队列按原 operationId 恢复。

编码异常另保留一份失败候选，计入未保存状态。重试重新编码；新编辑替代旧失败候选；失败不能被重试入口误清为“已保存”。原字符串调用方式继续兼容。

## 可重复的性能检查

`开发工具/保存提速.test.mjs` 加载真实 Zustand persist 和装配后的画布存储，通过局部 JSON 包装计数，不替换全局 JSON。

合成场景：20 个产品，各 250 个节点，共 5000 节点；每个节点 1000 字符。一次防抖窗口内更新同一产品视区 100 次，最终 JSON 5,999,329 字节。

| 指标 | 原调用方式 | 修改后 |
| --- | ---: | ---: |
| 全量 JSON 编码次数 | 100 | 1 |
| 编辑、排队阶段编码次数 | 100 | 0 |
| 最后一轮定向检查的累计编码时间 | 1193.89ms | 11.04ms |
| 最终 JSON 内容 | 基准 | 与基准逐字相同 |

耗时来自当前电脑 Node 进程的合成数据测量，受负载和 GC 影响；不是浏览器帧率、峰值内存或所有工作负载的速度承诺。较长连续输入仍按最长等待周期提交，不能理解为所有输入只保存一次。

还覆盖：

- 真实 Zustand 连续 100 次编辑只编码最终稿；仅 hydrated 等运行状态变化不触发编码。
- 250ms 最长等待和立即排空；慢写入期间 20 次编辑不提前编码，只提交最新候选。
- 编码失败、连续重试失败、修正后恢复；状态与真实回执一致。
- 底层提交前同步抛错时保留已经编码的候选；重试不能因为缓存相同而跳过真正提交。
- 批量保存门控放行的最终检查点即使延迟编码，也不读取之后被门控的内存进度。
- 当前单文档 SQLite 适配器丢失回执后，只恢复原请求；编码一次、根文档 revision 为 1，冷读取内容完整。
