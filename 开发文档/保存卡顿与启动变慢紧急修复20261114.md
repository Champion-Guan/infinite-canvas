# 保存卡顿与启动变慢紧急修复

## 已确认原因

本次此前创建的大图验收样本`planning-size-main-20261114`在画布JSON中保留
12张4MiB图片的data URL，并在策划来源parameters文本内再次复制这些图片。
原始类型树中12个URL各5,592,430字符，来源快照67,111,057字符。
这是本次验收工具引入的数据膨胀问题，不能归因于用户产品图或单纯的服务商上限。
当前编码器只将blob URL移入媒体，未处理有稳定storageKey的data URL。

故障时Chrome renderer持续占用超过一个核，sample记录physical footprint
6.7GB、峰值7.1GB。本机HTTP仍200，页面报无响应，正常重载和导出无法执行。

## 数据及代码修复

- 正常排空停止开发服务后，只定向修复本次验收样本，不删除任何画布或节点。
- 12张图片写入现有媒体存储，SHA256内容去重，只需保留1份相同图片；
  写后读取并逐字节核对。原图不缩放，原storageKey和图片属性保持。
- 来源快照有稳定文件键时移除重复内嵌URL，保留文件键与其余参数。
- 应用根JSON从143,645,533字节减少到9,428,408字节；
  163个产品和验收产品4个节点均保留。
- 编码器新增对`url`字段且有storageKey的图片data URL的媒体转换，
  后续编辑复用确认的媒体；普通文本和无文件键的独立data URL保持原样。
- `productPlanningParameters`不再将带稳定文件键的data URL复制到来源文本。
- 未修改保存ACK判断、保存队列、冲突保护或任务重试规则。

一次性修复工具：`开发工具/修复大图验收内嵌数据.mjs`，
只接受代码中固定的验收产品和参数卡，需正常停服后运行。

## 当前实页结果

旧页无法响应正常重载；保留旧页，在同一个Chrome、同一3000服务载入恢复页。
先核对SQLite中当前画布两张卡片、英文、文本模式均已落盘，恢复页呈现一致。
随后关闭旧无响应标签页；原renderer PID89823确认退出，没有退出Chrome。

- 恢复页首次canvas-painted：4074.8ms，状态“已保存”。
- 合成卡编辑文字：出现“保存中”，随后“已保存”；恢复原文亦成功。
- 刷新后原文完全相同；第二次canvas-painted：2973.0ms，
  visible-images-painted：2973.6ms，状态“已保存”。
- 切换大图验收画布：12张图片、提示词、对应配置完整，最终“已保存”。
- 没有发出模型生成请求。当前恢复页保留为工作台使用页面。
- 截图：`保存卡顿修复实页20261114.jpg`。

时间来自真实DOM的`data-startup-*`阶段标记，是两次本机观测，
不是所有电脑的启动时限保证。故障旧页面的内存编辑无法导出；
恢复依据已提交SQLite快照，已核对屏幕上的卡片和配置，不声称恢复未知的未提交事务。
